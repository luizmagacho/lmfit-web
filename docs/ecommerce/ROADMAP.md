> Customers buy products directly on the platform, per tenant (`{slug}.domain`), from catalog to paid order.

## 1. Current state (audited 2026-07-15)

A storefront skeleton **already exists**. The roadmap below is gap-driven, not greenfield.

### What already works

| Area | Evidence |
|---|---|
| Public catalog API | `lmfit-api/src/catalog/catalog.controller.ts` — `GET /public/catalog/categories`, `/products`, `/products/:slug` (tenant-resolved, no auth) |
| Storefront pages | `lmfit-web/src/app/(public)/catalogo/` — listing, PDP by slug (`catalogo/p/[slug]`), `checkout/`, `pedido/novo/` |
| Draft → real order | `order-drafts` module: public token flow, **server-side pricing** (retail/wholesale by qty), stock validation with backorder rules (`acceptsBackorder`/`backorderMinQty`), coupon support (mutually exclusive with wholesale price) |
| Payments plumbing | `payments` module: PIX payment records with TTL/expiration, InfinitePay webhook handler (`POST /public/payments/infinitepay-webhook` → `confirmInfinitePayPaymentPaid`), webhook dispatch with retry + dead-letter queue, Sentry capture |
| Ops foundation | Sentry on API with tenant/user tags; staff alerts on submitted drafts (`notifications`); WhatsApp module; audit decorators |
| Tenant branding | `tenant.schema.ts`: `logoUrl`, `faviconUrl`, `primaryColor`, `secondaryColor`, `darkMode`; plan/limits gating |
| Admin side | Products with variants (incl. price ranges + manual price protection), inventory multi-local, promotions, loyalty, fiscal, PDV |

### Confirmed gaps (what the loops close)

1. **Payments are simulated.** `createPixPayment` returns `DEV_PIX_PLACEHOLDER` on *both* provider branches; `createInfinitePayPayment` sets `checkoutUrl` to the local `/checkout/payment-simulation` page. No real money can move.
2. **No persistent cart.** The public flow is a single-session draft (`pedido/novo`); there is no cart that survives navigation/browsing, no variant picker UX on the PDP feeding a cart.
3. **No customer accounts.** `auth` module is staff-only (admin/staff roles). Buyers cannot log in, see order history, or reuse addresses.
4. **No shipping calculation.** Freight fields exist on drafts/orders, but the fee is manual — no CEP-based rates, no carrier integration, no pickup-vs-delivery choice.
5. **No buyer notifications.** Alerts go to staff only; the buyer gets nothing after paying (no confirmation, no status updates, no tracking page beyond the draft token).
6. **No storefront management for the tenant.** No on/off switch, banners, featured products, SEO metadata, or per-tenant payment/shipping settings in the admin.
7. **Launch hardening missing.** No rate limiting on `/public/*`, no Sentry on the storefront browser bundle, no analytics, SEO/CWV never measured, LGPD/cookie consent absent.

### Loop 0 — Baseline E2E (verify-first)

**Goal:** prove or disprove that the existing flow works: catalog → PDP → `pedido/novo` → draft submit → order created → PIX simulation → payment confirmed → order paid in admin → loyalty/stock effects. Fix only what blocks the walk-through.
**Deliverables:** executed checklist with screenshots, `ARCHITECTURE.md` (request flow diagram, module map), confirmed gap list feeding Loop 1 planning, one automated happy-path test (API-level: draft → submit → dev-confirm → order paid).
**Touches:** read-mostly; small fixes allowed anywhere. → Full spec: [specs/loop-00-baseline-e2e.md](./specs/loop-00-baseline-e2e.md)

### Loop 1 — Storefront UX ✅ (rescoped after Loop 0)

Loop 0 proved the original scope (cart, variant picker, checkout) already existed. Rescoped to the
real gaps and shipped 2026-07-15: `/pedido/confirmado` order-confirmation page wired into all three
post-submit paths; price ranges on catalog cards (varejo); `pedido/novo` response-shape fix;
floating-cart WhatsApp number from tenant config. Details: [specs/loop-01-storefront-ux.md](./specs/loop-01-storefront-ux.md).

### Loop 2 — Real payments + price display rules ✅

**Shipped 2026-07-15.** PSP question resolved by reading the code, not by picking one: InfinitePay's
real checkout-link generation already existed and works once a tenant has
`infinitePayTag`+`infinitePayApiKey` (form added to Settings). PIX has no standalone QR API from
InfinitePay, so `pix` now delegates to their same real hosted checkout (which offers Pix as a
method) via a dedicated "Pagar com Pix (N% OFF)" checkout button, with a safe fallback to the old
dev-QR placeholder when no real creds are set or the PSP call fails. Per-tenant
`pricingDisplay` (`pixDiscountPercent`, `maxInstallments`) ships on card, PDP, sacola and checkout,
applied server-side at submit only when `payment.method === 'pix'` (matches what's displayed).
REFINEMENT (reading the actual controllers before coding) found and closed **two pre-existing
security holes** that weren't in the original plan: `simulate-confirm` had zero auth in production,
and the InfinitePay webhook trusted an unsigned payload — both fixed. Also fixed a stale
`/pedido/novo` redirect and, discovered mid-VERIFY, a PDP display bug where every guest saw
wholesale prices due to the seed data's `minWholesaleQty:1`. Credential encryption and stock
reservation stay out of scope, carried to Loop 10 and Loop 3+ respectively. Full detail:
[specs/loop-02-real-payments.md](./specs/loop-02-real-payments.md).

### Loop 3 — Shipping & address

**Goal:** real totals before payment, and freight visible early (PDP).
**Scope:** CEP lookup (web already has `src/lib/cep`); per-tenant shipping config v1 = flat fee +
free-above threshold + pickup option (carrier quotes via Melhor Envio deferred to Loop 9+); shipping
choice in checkout; **PDP freight calculator by CEP** (V2); fee computed server-side into draft/order totals.
**Key ACs:** total shown pre-payment equals order total; pickup skips address; changing CEP re-quotes;
PDP quote == checkout quote for the same CEP.

### Loop 4 — Storefront V2: brand layer + Home + "Loja online" CMS ✅

**Goal:** the store looks like a brand, not a product grid — fully tenant-configured.
**Scope (blueprint §2.1–2.2, §2.9–2.10, §3):** **theme system — 8 selectable presets (Essencial /
Editorial / Performance / Boutique / Vibrante / Studio / Impacto / Monocromo) as design-token
bundles with live preview in admin, tenant primaryColor as accent** (blueprint §2.10); announcement
ticker; header v2 (search with autocomplete,
account, cart count, category menu); footer institucional; editorial Home with ordered blocks (hero
carousel, product vitrines, category tiles, trust bar, first-purchase coupon banner); institutional
pages (quem somos, como comprar, guia de medidas, contato) as CMS-lite; **Lookbook "compre o look"
module** (editorial photo → add all pieces to cart, no combo discount in v1); admin section **"Loja
online"** editing the whole `storefront` config with preview; store on/off switch; plan gating.
Note: the storefront home is a **new** route in `(public)` — none exists today.
**Key ACs:** two tenants render visibly different stores from config alone; store off → catalog 404s
within seconds; coupon banner ties into existing promotions.

### Loop 5 — Storefront V2: PLP + PDP ✅

**Goal:** discovery and product pages at fashion-e-commerce standard.
**Scope (blueprint §2.3–2.4):** public catalog API gains filters/sort/pagination
(`category/size/color/price/sort/page`); PLP with filter rail + sort; product card v2 (hover second
photo, color swatches, price with pix/installments, badges, quick-add); PDP v2: photo gallery with
zoom, color swatch + size button selector with stock states (replaces steppers), size-guide modal,
description/composition fields, resumo da política de troca, "you may also like" shelf (same category).
**Key ACs:** filters are server-side and paginated; size selector blocks esgotado and signals
sob-encomenda; gallery works with variant images; CWV budget respected on PLP/PDP.

### Loop 6 — Storefront V2: cart drawer + one-page checkout ✅

**Goal:** conversion-grade sacola and checkout.
**Scope (blueprint §2.5–2.6):** cart drawer mounted in the `(public)` layout replacing the floating
cart (any "Comprar" opens it without reload; line edit, coupon field, free-shipping progress bar,
cross-sell suggestions, "ou R$ X no Pix"); **one-page checkout** with progressive sections
(identificação → entrega → pagamento) and sticky order summary — evolves the existing
`CheckoutClient` (decision recorded in STOREFRONT-V2 §5); guest always possible; `/pedido/confirmado`
kept as final state.
**Key ACs:** drawer state == server-priced draft at submit; coupon errors inline; section state
survives reload; funnel works logged-out end-to-end.

### Loop 7 — Customer accounts ✅

**Goal:** returning buyers.
**Scope:** customer auth separate from staff JWT; `/conta`: meus pedidos (status + payment), addresses
CRUD; checkout pre-fill and fast-login at identificação step; link guest orders by e-mail on first
login; loyalty points balance.
**Key ACs:** customer tokens cannot reach staff endpoints (guard-level test); tenant isolation on
every `/me/*` query; guest checkout still works.

**REFINEMENT decisions locked in (2026-07-16):**
- **Login mechanism: e-mail magic link only**, not WhatsApp OTP. Codebase research found zero
  outbound WhatsApp send capability anywhere (`src/whatsapp/` is inbound-only) — building OTP-via-WhatsApp
  would mean building the entire outbound Meta Graph API integration from scratch, which is out of
  proportion to this loop. A working `NotificationsService.sendEmail` already exists and is reused as-is.
- Mirrors the existing staff-JWT pattern exactly but as a fully separate track: new Passport strategy
  `'jwt-customer'` + `CustomerAuthGuard`, own secret (`JWT_CUSTOMER_ACCESS_SECRET`), own refresh-token
  collection — so a customer token can never reach a staff-only route by construction, not just by convention.
- `Customer.addresses[]` will be reshaped from its current `{label, street, city, state, zip, country}`
  shape to the CEP-shaped fields checkout's `AddressForm` already uses (`cep, logradouro, numero,
  complemento, bairro, cidade, uf`) — confirmed safe: no admin UI edits this field today.
- **Real order tracking (carrier + tracking code) does not exist anywhere in the schema** — `/conta`
  can only show `shippingMethod` (free text), not a real tracking number. Carried over, not built here.
- While deciding the login mechanism, the user described a much larger vision — merchant-connected
  WhatsApp Business + AI-handled customer conversations + AI-assisted staff sales via chat/voice.
  Explicitly deferred as its own future initiative, not part of this loop. See **Loop 11** below.

**Shipped 2026-07-17.** New `CustomerAuthModule` (lmfit-api): `'jwt-customer'` Passport strategy +
`CustomerAuthGuard` (tenant cross-check, mirrors `JwtAuthGuard`), `MagicLinkToken`/
`CustomerRefreshToken` schemas (same hash-at-rest + TTL-index pattern as staff's `RefreshToken`),
`PublicCustomerAuthController` (request-link/verify/refresh/logout, no guard) + `CustomerMeController`
(`/me/profile`, `/me/orders`, `/me/addresses` CRUD, guarded). `Customer.addresses[]` reshaped to
CEP-shaped fields matching checkout's `AddressForm` exactly, with real `_id`s. Extended the existing

## 2.1 Ondas 2026 — próximos loops (26–33 + Voz-A/B)

Derivadas da análise competitiva de agosto/2026 em [MERCADO-2026.md](./MERCADO-2026.md), que cruzou
o que os concorrentes entregaram em 2026 com uma auditoria do que **de fato existe no código**.
Racional da ordem: **diferencial não segura cliente que perdeu a venda no frete ou no checkout** —
primeiro tapamos o que nos faz perder comparação direta, só depois investimos onde somos únicos.

### Onda 0 — parar de perder venda

**Loop 26 — Canário do caminho do dinheiro (S).** O bug de atacado de 12/08 passou por 437 testes
verdes porque o mock usava `priceWholesale (35) < priceRetail (50)` — forma de dado que quase não
existe na base real, onde a maioria das variantes tem os dois valores iguais (fallback de
`getWholesalePricingBatch()`). A forma real nunca foi exercitada. **Escopo:** teste de integração
sem mock de pricing cobrindo catálogo → draft → patch → submit com dados no formato de produção
(variante sem atacado, com atacado real, 1 unidade, no limite do mínimo, estoque baixo/zero com e
sem backorder); pedido sintético diário num tenant de teste em prod; alerta quando
`POST /public/order-drafts/:token/submit` responder 4xx acima de um limiar — hoje o cliente vê o
erro e a loja não fica sabendo.

### Onda 1 — table stakes que travam conversão

**Loop 27 — Frete real, Melhor Envio (M).** Hoje o frete é só `standardFee`/`expressFee`/
`freeAboveTotal` no tenant; não há **nenhuma** referência a transportadora no repo. A UI de escolha
de frete e o lookup de CEP já existem desde os Loops 3/13 — falta o cotador real por trás, etiqueta
e rastreio no pedido.

**Loop 28 — Pix nativo + Pix Parcelado (M).** O Loop 2 resolveu Pix delegando ao checkout hospedado
da InfinitePay; o cliente sai da loja para pagar. Pix foi 42% do valor transacionado no e-commerce
brasileiro em 2025. **Escopo:** QR/copia-e-cola dentro do nosso checkout + webhook de confirmação,
expondo Pix Parcelado quando o PSP suportar, e deixando a fundação pronta para Pix Automático
(recorrência → clube/assinatura).

**Loop 29 — NF-e automática no pedido pago (M).** `FocusNfeAdapter` é real e funciona, mas nenhum
ponto em `orders/` ou `payments/` chama o `FiscalService` — emissão é 100% manual hoje. **Escopo:**
gatilho ao marcar pago/enviado, com fila e reprocesso em falha (a SEFAZ cai; não pode travar o
pedido).

### Onda 2 — aquisição e recuperação

**Loop 30 — Feed de produtos (M).** Um endpoint gerando o catálogo em Google Merchant (XML),
Catálogo Meta (destrava Instagram Shopping/Advantage+) e o formato do Agentic Commerce Protocol
(Stripe + OpenAI), que alimenta o ChatGPT Shopping. Barato porque `listPublicCatalog`, SEO e JSON-LD
já existem; alto retorno porque sem feed não há tráfego pago em escala nem presença em busca por IA.

**Loop 31 — Pós-venda e carrinho abandonado por WhatsApp (S).** `abandoned-cart.cron` só chama
`notify.sendEmail`, e o público do LM FIT não abre e-mail. Reusa o `WhatsappSenderService` já pronto
desde o Loop 11-A para sacola abandonada, "pedido confirmado" e "pedido enviado + rastreio".

### Onda 3 — diferenciação (onde ganhamos sozinhos)

> ⚠️ Contexto que reforça esta onda: a Meta lançou em jun/2026 um agente de IA nativo no WhatsApp
> Business que responde, recomenda e "conclui venda". O bot que só conversa está virando commodity
> de graça — o que não vira é o agente que **executa no ERP** com estoque e preço reais (Loop 11-C).

**Voz-A / Voz-B — venda por voz no WhatsApp (M cada).** Plano completo já escrito em
[`misty-launching-moth`](../../../.claude/plans/misty-launching-moth.md). Renumerados de "12-A/12-B"
para **Voz-A/Voz-B**: o plano original colidia com o Loop 12 (storefront multi-layout), que já
existe. Voz-A é ingestão (baixar mídia da Meta + transcrever); Voz-B é o achado crítico do plano —
o pipeline de staff hoje cria pedido `open` e **não baixa estoque**, mesmo por texto; precisa passar
pelo `syncBatch` como o PDV faz.

**Loop 32 — Portal da Revendedora, B2B (L).** Hoje `/catalogo` é único e igual para todos. A
ViaShopModa já vende exatamente isto: catálogo por revendedora, pedido mínimo, tabela de preço
diferenciada, carteira de clientes. É o modelo de negócio real do LM FIT.

**Loop 33 — IA para o lojista (M).** Gerar nome, descrição, SEO e alt-text a partir da foto do
produto — a chave Gemini já está no tenant e o `LlmService` já existe. A Nuvemshop reporta que 72%
dos lojistas da base já usam IA para isso: é expectativa de mercado, não novidade.

### O que decidimos **não** fazer agora

- **Mais presets de layout.** O V4 já entregou diferenciação visual acima do mercado; o retorno do
  11º preset é próximo de zero comparado a ter frete real.
- **Marketplace próprio.** M•A•R e Brás Online ocupam esse espaço, e é negócio de rede, não de software.
- **PCP/MRP profundo.** Não dá para ganhar do Sisplan em profundidade de indústria, e não é onde
  está a dor do nosso cliente.
