# Loop 02 — Real payments + price display rules

**Status:** Done (2026-07-15)
**Roadmap entry:** ROADMAP.md §Loop 2 · **Depends on:** Loop 1
**Repos touched:** lmfit-api / lmfit-web

## Goal

Money actually moves; orders flip to paid without staff action. Storefront shows consistent, 
tenant-configurable pricing rules (R$ X com Pix desconto, Nx sem juros) everywhere (cards, PDP, 
sacola, checkout), and those rules are honored at charge time.

## Scope

**In:**
- Real PIX QR generation (retire `DEV_PIX_PLACEHOLDER`)
- PSP decision + implementation (InfinitePay vs. Mercado Pago vs. Pagar.me)
- Per-tenant credentials storage (encrypted like `focusNfeToken`)
- Per-tenant pricing display rules (`pricingDisplay: { pixDiscountPercent, maxInstallments }` in 
  `storefront` config)
- Admin config UX for PSP credentials + pricing rules in "Loja online" settings
- Payment status page with polling (customer sees "Aguardando pagamento...")
- Webhook signature validation (prevent spoofed confirms)
- Expiration → order canceled + stock released (if reserved; today not reserved)
- Sentry capture for payment errors

**Out (explicitly):**
- Carrier quotes via Melhor Envio (Loop 9)
- Card fraud detection (starter integration; full rules in hardening)
- Multiple PSPs per tenant (one active PSP per tenant in this loop)
- Loyalty credit at payment (already fires at `completed`; no change)

## Decisions

| Decision | Choice | Why |
|---|---|---|
| PSP for v1 | **InfinitePay — confirmed** (no longer tentative) | Code inspection: `createInfinitePayPayment` already POSTs to `api.checkout.infinitepay.io/links` and returns a real `checkoutUrl` when `tenant.infinitePayTag`+`infinitePayApiKey` are set (both fields already exist on `tenant.schema.ts:117,120`). Only the **PIX QR** is a placeholder (`provider === 'dev' ? DEV_PIX_PLACEHOLDER : DEV_PIX_PLACEHOLDER` — literally the same value either branch, `payments.service.ts:39`). Scope shrinks to: real PIX QR + close the two security gaps below |
| PIX provider | Real when a real PSP PIX endpoint is wired; `dev` stays the local fallback | Keeps dev iteration fast; the `provider` branch already exists, it just needs a real implementation instead of the placeholder on both sides |
| Credential storage | **Plain field on `tenant` schema, same as `focusNfeToken` / `IntegrationCredentials`** — no new encryption layer this loop | Checked: **no encryption precedent exists anywhere in the codebase** — `focusNfeToken` (`tenant.schema.ts:53`) and every `IntegrationCredentials` field (`integration.schema.ts:19-27`) are plain `@Prop()` strings. Original spec assumption ("encrypted like focusNfeToken") was wrong. New crypto infra is out of this loop's size budget — filed as a hardening carry-over (Loop 10) instead of invented ad hoc |
| Stock reservation | Not this loop (stays at current: `completed` order decrements) | Oversell risk documented; requires draft→reserved state + expiration cleanup; later loop |
| Card data | Never touch our servers; PSP checkout handles it | PCI scope stays with PSP; `checkoutUrl` redirect model |
| `simulate-confirm` in production | **Gate behind the same `PAYMENT_DEV_CONFIRM_KEY` header check as `dev-confirm`, or remove the route in prod** | **Blocking finding** (REFINEMENT): `POST /public/payments/:id/simulate-confirm` has **zero auth** today (`public-payments.controller.ts:47`) — anyone who knows/enumerates a `paymentId` can mark it paid without ever paying, in production. Same severity class as Loop 0's 422 — found only by reading the controller, not by assumption |
| Webhook signature | Verify InfinitePay's signature header if their API exposes one; otherwise fall back to a shared-secret query param on the `webhook_url` we control | **Blocking finding** (REFINEMENT): `POST /public/payments/infinitepay-webhook` (`public-payments.controller.ts:54`) trusts `body.order_nsu` with **no signature check at all** — anyone can POST `{order_nsu: "<paymentId>"}` and flip any pending order to paid. Exact mechanism confirmed during IMPLEMENT against InfinitePay's real API; either way AC7 does not close without one |

**3 bugs found and fixed mid-VERIFY** (not in the original task list — logged here per process
Phase 3 "blockers → spec task, never improvised"):
1. `updatePricingDisplay` didn't invalidate `TenantsService`'s 5-min `slugCache` — the storefront
   kept serving the pre-save pricing rule for up to 5 minutes after an admin saved it. Fixed by
   adding `this.slugCache.delete(doc.slug)`, matching `updateBranding`'s existing pattern.
2. **PDP display bug** (pre-existing, not introduced by this loop): `VariantGrid` computed each
   row's reference price via `resolveUnitPrice(...,qty=1,role)`, which factors in
   `qty >= minWholesaleQty`. Every seed product has `minWholesaleQty:1` (Loop 0's documented data
   quirk), so `1 >= 1` was silently promoting **every anonymous visitor to wholesale pricing on
   the PDP** — e.g. Real Madrid shirt showed R$299,90 to a guest instead of the real R$200,00
   retail price. Confirmed via `useCartStore` that the actual cart/checkout price is computed
   independently from real added quantity (so nothing was mischarged), but the PDP was
   *displaying* the wrong number to every retail visitor — this was purely cosmetic-but-wrong
   until now. Fixed by making the PDP's reference price role-only (`inferModeForUser(role)`),
   matching how the catalog card (`ProductGrid`) already computed it; the cart's own
   quantity-based wholesale upgrade is untouched and still correct.
3. Dev environment hygiene: the API process had drifted to a stale compiled `node dist/main`
   (no hot reload) partway through IMPLEMENT, then crashed with `EADDRINUSE` on a watch-mode
   restart, leaving two processes racing for port 4000 — silently serving pre-Loop-2 code for a
   stretch. Not a product bug, but cost real debugging time; killed both and restarted clean.

## Result

**Shipped:** real payments infrastructure for InfinitePay (PIX now delegates to their real hosted
checkout instead of a placeholder QR, with a safe dev fallback), per-tenant Pix-discount +
installment display wired into all 4 storefront surfaces (card, PDP, sacola, checkout) with a
matching server-side charge, a dedicated "Pagar com Pix" checkout option, admin settings UI, and
two closed security holes (unauthenticated `simulate-confirm`, unsigned webhook) that were live in
production before this loop — found by reading the controllers during REFINEMENT, not assumed.
16 new/updated tests (54 API total, 165 web total, all green).

**Scope changes from the original draft** (all recorded live in the Follow-up record above):
- PSP decision resolved to "no decision needed" — InfinitePay was already real; scope shrank to
  finishing PIX + fixing the two security gaps, freeing budget for the pricing-display half.
- PIX doesn't get its own hand-rolled BR Code QR (architecturally not viable without a bank/PSP
  relationship of our own); it reuses the real InfinitePay checkout, selected via a distinct
  checkout button so the discount can still be applied deterministically server-side.
- Credential encryption dropped in favor of matching the existing (unencrypted) codebase pattern;
  carried over to Loop 10 hardening rather than invented ad hoc.

**Bugs found and fixed that weren't in the task list** (see VERIFY section above for full detail):
tenant-config cache invalidation gap, a pre-existing PDP wholesale-pricing display bug (guests
saw wholesale prices on every product due to the seed data's `minWholesaleQty:1`, unrelated to
Pix), and a local dev-environment process conflict.

**Deviations:**
- AC6 and the AC10 production-block path were verified by unit test only, not reproduced live
  (would need clock manipulation / a prod build respectively) — same trade-off Loop 0 made for
  its equivalent tests, judged acceptable here too.
- The full end-to-end browser walk was completed in two halves (browser for the four display
  surfaces + admin config, curl for the payment-mechanics half) after the local API process
  crashed and invalidated the browser session mid-walk — documented as bug #3 above, not a
  shortcut taken by choice.

**Retro:**
- *What helped:* reading the actual controllers in REFINEMENT before writing any code caught two
  real security holes and a stale redirect that a "trust the spec" implementation would have
  shipped as-is — REFINEMENT earned its place in the v2 process on its first real use.
- *What hurt:* verifying pricing display required clearing three different pieces of
  browser-persisted state (auth token, cart's own cached `role`, tenant's server-side
  `slugCache`) before the "clean guest" scenario was actually clean — each one silently made the
  UI show stale data with no error, costing real debugging time. Worth a carry-over.
- *Process note:* "blockers → spec task, never improvised" (IMPLEMENT ground rule) held even for
  bugs discovered mid-VERIFY — the cache-invalidation and PDP-display fixes were reasoned through
  and recorded before touching code, not patched reflexively.

**Carry-overs → Loop 3+ / backlog:**
- `minWholesaleQty:1` on all seed products (Loop 0's original finding) is confirmed to leak into
  real pricing paths (cart, order-drafts submit) beyond just display — still explicitly out of
  scope for a payments loop, but its blast radius is now known to be larger than "cosmetic".
- Credential encryption (Loop 10 hardening, per Decisions table).
- Any staging/production secret rotation UX for `PAYMENT_WEBHOOK_SECRET` / `PAYMENT_DEV_CONFIRM_KEY`
  — currently plain env vars, fine for now, revisit alongside credential encryption.
